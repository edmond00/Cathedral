This file is READ BY THE GAME, so keep the "llama.cpp build: bNNNN" format on the first line.
LlamaInstallCheck (src/LLM) asks llama-server for its real build at startup and warns, on the
loading screen and the main menu, when that build differs from LlamaInstallCheck.ExpectedBuild
or from the number written here. Each GPU backend pack carries its own BUILD.txt, checked the
same way. Upgrading: see the `models` skill.

── what this folder is ───────────────────────────────────────────────────────

The NATIVE ARM64 toolchain, used on Windows-on-ARM machines (Snapdragon X and successors).
LlamaRuntime picks it over ../llama when RuntimeInformation.OSArchitecture is Arm64 and this
folder exists; otherwise it falls back to ../llama and runs emulated, which is what happened
before this folder shipped.

It is chosen by DETECTION, NOT BY THE PROBE. An architecture is not a backend: an ARM64 DLL
cannot be loaded into an x64 process, so there is nothing for LlamaProbe to measure between
the two. Nor is there anything to decide — measured on a Snapdragon X (X126100) against the
shipped 3B model, native beats the same machine running the x64 build under emulation:

    prompt read    76.1 tok/s native  vs  13.6 emulated   (5.6x)
    generation     13.8 tok/s native  vs   5.4 emulated   (2.6x)

Those figures were measured on b8746; this folder is now b11515 and has not been re-measured on
ARM hardware.

The build number may differ from ../llama's (it currently does not). That is fine and not the hazard the
backends README warns about: each toolchain carries its own complete set of ggml libraries, so
nothing is mixed ACROSS folders. What must never differ is a backend under backends/ versus the
ggml-base.dll beside it in the SAME folder.

── what was kept, and why ────────────────────────────────────────────────────

Pruned the same way as ../llama, and for the same reason: the game runs two executables, and
every extra unsigned .exe is another SmartScreen/antivirus prompt for a player.

kept:
  llama-server.exe        the only thing the game actually runs
  llama-bench.exe         the first-run probe measures backends with this
  llama-server-impl.dll, llama-bench-impl.dll   the programs themselves; each .exe is a launcher
  llama.dll, llama-common.dll, ggml.dll, ggml-base.dll, mtmd.dll
  ggml-cpu.dll            one, not fourteen — see below
  libomp.dll              OpenMP runtime the CPU backend links against (was libomp140.aarch64.dll)
  LICENSE-LLVM-OpenMP     its license, since we redistribute it

dropped:
  ggml-rpc.dll, ggml-rpc-server.exe    distributed inference across machines
  llama-cli/-tts/-imatrix/-quantize/-perplexity/-mtmd-*/-qwen2vl-* and the rest

That is 22 MB against 84 MB unpruned. Dropping the multimodal CLI front-ends does not cost
multimodal support: mtmd.dll stays because llama-server.exe imports it directly.

An ARM64 binary cannot be executed on an x64 host, so "does it still start?" is not a check
available from a dev machine. Verify a re-prune by reading the PE import tables instead: the
import closure over llama-server.exe and llama-bench.exe must be satisfied by the files above
plus MSVCP140.dll, which upstream ships in neither architecture's zip and comes from the VC++
redistributable.

── differences from the x64 folder ───────────────────────────────────────────

One ggml-cpu.dll, not fourteen. The x64 build ships a variant per microarchitecture
(haswell, skylakex, zen4, …) and picks by host ISA at load; ARM64 has no such fan-out, so
package.ps1's "expected the full set" check applies to the x64 folder only.

No backends/ folder. There is no GPU backend worth shipping here: the Adreno X1-45 in current
Snapdragon X parts reads prompts through Vulkan at 1.1 tok/s against this toolchain's 76.1 on
the CPU, so the probe would measure it and reject it. With no backends/ directory the probe
skips benchmarking entirely and settles on CPU for free, which is also the right answer.
